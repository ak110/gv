# 自己更新の復旧可能性

`src/updater.rs`の`build_update_batch_bytes`が生成したバッチを
`src/updater/exhaustive.rs`で台本として読み、配置済み新版か旧版を復旧に使えること、
必要な配置を終えるまで完了・起動・成功終了に進まないことを試験する。
新しい命令を追加した場合は、対応するファイル操作と分岐を試験側に反映する。未対応の命令は試験を失敗させる。

## 再実行

Windowsで次を実行する。Linuxではコンパイルまで行い、合否はWindows CIで判定する。

```powershell
mise exec -- cargo test --locked updater::exhaustive::
mise exec -- cargo test --locked updater::exhaustive:: -- --ignored
```

初期状態では準備済み新版が作業領域にあり、配置先に有効な旧版がある。
退避ファイルの有無と、付属ファイル1〜2件を列挙する。
モデルの1手は生成済みバッチの命令1件であり、ファイル操作の成功、失敗、対象が残る部分失敗を分ける。
到達した状態を再訪しても探索し直さないため、同じ状態へ戻る再試行の回数に上限を設ける必要はない。
各到達状態で中断した時に復旧できるかを確かめる。

明示実行側では各中断点から同じバッチを先頭から1回再実行する。
復旧できない状態は、実際の生成バッチを使ってWindows上でも確認する。
退避直後に中断し、再実行で退避を削除した時点が反例候補である。
ステージされた未配置新版は、配置済みの実行ファイルとして数えない。

`cmd.exe`の構文・Windowsの原子性・電源断後の永続性はモデルの保証外である。
バッチ起動前は、ダウンロードの疑似中断、ZIP・単体実行ファイルの展開先やバッチ保存先の障害、起動失敗、成功を別の試験で実関数に与える。
作業領域とインストール先の外のファイル、および既存の実行ファイルが変わらないことを、隔離した作業領域で確かめる。
ネットワークとプロセス起動は差し替える。後始末は実装が呼ぶ関数に同じ隔離領域を与えて退避だけを削除することを確かめる。

## 追従

試験が欠陥を検出することは付属ファイルのコピー失敗時の分岐を生成コードから一時的に外し、
早すぎる完了を検出することと、復元後の結果を比較して確かめる。
Win32や`cmd.exe`の実挙動は`src/updater.rs`の結合テストと比較する。

試験を実行して結果を確認した後にだけ、次のコマンドで追従記録を更新する。

```shell
uvx --exclude-newer-package pyfltr=false pyfltr verification-sync --update .claude/skills/update-recovery/SKILL.md
```
